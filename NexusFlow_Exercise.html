Section 1

Business Context

NexusFlow is a B2B SaaS company selling workflow automation to mid-market companies.

Company Profile

  • ~500 customers across 3 regions (NA, EMEA, APAC)
  • 5 subscription plans — Free through Enterprise
  • Monthly billing with usage-based overages
  • Support operations + product telemetry
  • Operating for 18 months

Key Challenge

Data exists in CSV exports from various source systems. Three monthly batches are available (January, February, March 2024). Multiple internal teams have documented their business rules, but they don’t always agree on metric definitions. Your job is to build the data platform that resolves this.

Section 2

Your Assignment

Build a complete data platform from the provided CSV files. You choose the tools and architecture. We recommend PostgreSQL + Python, but any defensible stack is acceptable.

Database

Set up a database. Load, clean, and model data through a layered architecture (e.g., raw → stage → core → mart).

ETL Pipeline

Build transforms that handle deduplication, identity resolution, data quality, and incremental loading.

Data Model

Design an analytical model (star schema or similar). Fact tables, dimensions, appropriate SCD strategy.

Dashboard

A lightweight web application or report with charts, filters, and key business KPIs.

Access Control

Implement role-based access. At minimum: admin, analyst, viewer, regional manager (region-filtered).

Data Quality

Anomaly detection, reconciliation between layers, quarantine strategy for bad data.

Deliverables

  • Working database with all layers populated
  • ETL scripts — idempotent and restartable
  • Schema DDL files for all layers
  • Functional analytics dashboard with access control
  • decision_log.md — your choices, tradeoffs, and rejected alternatives
  • architecture.md — design documentation
  • Data quality checks and reconciliation report
  • Change request response (see Section 6)
  • README with setup instructions so we can run your solution
Tech stack guidance: We recommend PostgreSQL for the database and SQL & Python for ETL/application, but any reasonable stack is acceptable. Use whatever tools you’re most productive with — including AI assistants.

Section 5

Business Rules — Read Carefully

Three teams have documented their KPI definitions. They do not agree. You must decide the canonical definitions and document why you chose each one — including what you rejected.

This is critical. Read all three documents below before making any metric decisions. The conflicts are intentional. Your decision log is a key deliverable.

Finance Team VP Finance — Sarah Chen, Jan 15 2024

  • MRR: Active subscription amounts only. Usage overage is NOT included. Recognized on invoice date.
  • Churn MRR: Full cancellations only. Downgrades are “Contraction” and excluded from churn for board reporting.
  • NRR: (Starting + Expansion - Churn) / Starting. Contraction deliberately excluded.
  • Revenue recognition: At invoice date, not payment date or service delivery date.
  • Customer churn: All subscriptions terminated.
  • Free tier: Included in customer counts, NOT in revenue metrics.
  • Currency: All amounts USD. No multi-currency support needed.

Product Team VP Product — Marcus Rivera, Feb 10 2024

  • MRR: Subscription base + trailing 3-month average usage overage. Recognized on effective date (service delivery).
  • Churn MRR: Cancellations + “silent churn” (zero usage for 90+ days, even if paying).
  • NRR: (Starting + Expansion - Contraction - Churn + Reactivation) / Starting. Includes contraction.
  • Revenue recognition: Service delivery period, not invoice date.
  • Customer churn: Usage below threshold (<10 API calls AND <1 login/month) for 90 days, regardless of subscription status.
  • Free tier: Included in engagement and adoption metrics.

Sales Team CRO — Jake Torres, Jan 28 2024

  • Expansion MRR: Any MRR increase — upgrades, add-ons, price increases, usage overage growth.
  • Churn: A customer is NOT churned if they have any active subscription. Payment = customer. Period.
  • Customer count: Do NOT count free-tier. Active = paid plan only.
  • Contraction: Not tracked separately. Downgrade + staying = retained customer.
  • Win Rate: Won / (Won + Lost). Exclude open deals and churned deals.
Your task: For each conflicting metric, choose a canonical definition, justify it with a business rationale, and document the alternatives you rejected. Put this in your decision_log.md.
Section 6

Change Request #001

After your initial implementation, read this change request. For each item, write an impact analysis. Implement CR-1 if time permits.

CR-1: Regional Manager Role with Row-Level Security

Add a “Regional Manager” role. Each manager sees only their region’s data (NA, EMEA, or APAC). Enforced at the data layer, not just UI.

Answer: How do you implement this? How does it affect queries and API? What about company-wide aggregate KPIs?

CR-2: NRR by Contract Effective Date

Finance wants NRR calculated using the contract amendment effective_date instead of invoice date. Some amendments are retroactive.

Answer: Impact on fact tables? Need to restate historical data? How to handle amendments with effective dates before subscription start?

CR-3: New Partner Referral Source

New file partner_referrals.csv with partner_id, partner_name, referred_customer_name, referred_customer_email, referral_date, status. No customer_id — you must match by name or email.

Answer: Integration with customer dimension? Matching strategy? How to handle partial matches and non-matches?

Section 7

What We Evaluate

We evaluate thinking and documentation, not just code.

What Matters

  • Data modeling decisions and tradeoffs
  • ETL architecture — idempotency, error handling
  • Data quality reasoning — anomaly detection, triage
  • Business rule resolution and documentation
  • Code quality and testing
  • Decision log with rejected alternatives
  • Security / access control design

What Doesn’t Matter

  • UI aesthetics (functional beats pretty)
  • Speed of execution
  • Whether you used AI tools (use any freely)
  • 100% completion (depth beats breadth)
  • Which specific tech stack you chose
Important: We DO evaluate whether you understand what you built. Be prepared to explain every design choice verbally in a follow-up conversation.
Section 8

Hints

Use sparingly. Part of the exercise is discovering things on your own.

  • Profile your data before writing transforms
  • Customer IDs are not always what they seem
  • Not all timestamps use the same timezone
  • Some apparent “errors” are actually valid business records
  • Read all three business rules documents before choosing metrics
  • Think about what happens if your pipeline runs twice
  • Later batches introduce new files and corrections to earlier data
